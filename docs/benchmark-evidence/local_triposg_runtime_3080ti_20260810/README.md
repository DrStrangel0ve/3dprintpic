# Local TripoSG Runtime Recovery

## Result

The production `POST /run/image-to-mesh` path was recovered on the local
RTX 3080 Ti and verified with the exact recommended profile: TripoSG at 50
steps, guidance 7.0, 40,000 requested faces, adaptive voxel-close repair, and
no convex-hull fallback.

The fixed smoke returned HTTP 200 in `108.263 s` and emitted a printable STL.
The source image and meshes are intentionally not committed because the input
was a private local photo. Aggregate diagnostics and artifact hashes are kept
here so the runtime result remains auditable without publishing the subject.

## Root cause

Two independent failures were reproduced:

1. The relief backend retained SAM3/depth models while the planner launched an
   8.4 GB TripoSG checkpoint in a second process. On a 12 GB GPU and 16 GB host,
   the child crashed in `torch_cpu.dll` with Windows exception `0xc0000005`
   before inference.
2. After freeing that memory, current PyTorch loaded TripoSG in half precision
   but passed float32 hierarchical-grid coordinates to the half-precision VAE
   query projection. The decoder failed with `mat1 and mat2 must have the same
   dtype, but got Float and Half`.

The product now releases selection, depth, and dormant inpaint caches through
the local relief backend before CUDA TripoSG work, serializes image-to-mesh
jobs, loads TripoSG directly in fp16 with low CPU memory usage, and casts VAE
query coordinates only at the projection boundary. The source patch is
generated by `backend.benchmark.patch_triposg_sources` and is idempotent.

## Decision

This is a runtime repair, not a new model promotion. TripoSG remains the one
production single-image full-mesh model because its held-out ten-object run is
still the strongest promotion-eligible STL result. The fix changes resource
handoff and numeric compatibility, not the selected model or its quality gate.
